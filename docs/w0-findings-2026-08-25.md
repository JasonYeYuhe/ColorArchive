## W0-4:「那 86 个撞墙会话」这个群体定义本身是错的

又一次「先读发射点」:`word_paywall_hit`(`word-color-generator-page.tsx:378`)
只在 `words.length >= FREE_GENERATIONS` 的**实时跨越**时发,而 `words` 是
**localStorage 持久化**的数组。声明处的注释自己写了:
*"first-ever crossing of the free limit **this browser**"*。

- 所以那 85 个会话是**「这个浏览器有史以来第一次跨过 5 次」**,不是「撞了墙的会话」。
- 回访时已经被墙的人发的是 `word_paywall_restored`(:318),**永远不发 `hit`**。
- **85 事件 / 85 会话** 这个 1:1 不是巧合,是「每浏览器一生一次」的定义决定的。

→ **存在第三个群体:41 个会话,一到站就已经在墙后面**,只要按 `word_paywall_hit` 过滤就完全看不见。

生成深度 5 vs 1 的差距**部分是定义造成的**(你正是靠生成 5 次才到达墙),不是独立发现。
真正有信息量的是 B 组:**275 个会话里 145 个只生成了 1 个词就结束了。**

## W0-3:WordIntentProbe —— **问题不成立,因为问的方式是坏的**

`word-intent-probe.tsx:79` 的曝光事件在一个 `useEffect(…, [])` 里发。
**它数的是 mount,不是「被看到」。** 没有 IntersectionObserver、没有 dwell ——
而这个仓库**自己就有** `src/lib/use-impression.ts`,存在的理由正是「mount ≠ 曝光」,
偏偏这个组件没用它。

所以 **「241 次曝光 / 62 会话、0 作答、0 关闭」从来不能支持「人们看见了但无视它」。**

两条佐证:
- **两个会话分别在 49 秒里发了 50 次、8 秒里发了 25 次**,且 `page_read` 和
  `word_generated` 都是 0 —— 仅这两个疑似非人类会话就占了全部曝光的 **31%**;
  约 56% 的相邻曝光间隔 ≤5 秒。
- mount 门 `wordHistory.length >= 2` 从 **localStorage 惰性初始化**,
  所以**回访者一进页面就满足**,组件注释说的「看过一个自己的词之后才出现」只对首次访问者成立。

**真实曝光数被夹在 `10 ≤ E ≤ 63` 之间**(下界=有证据滚到探针以下的会话,上界=mount 过的会话)。
用 rule of three:E=10 → 作答率 95% 上界 ≈ **30%**;E=63 → ≈ **4.8%**。

> 🔴 **对抗性复核推翻了第一版调查的结论。** 调查员写「诚实的分母**至多** 10」——
> **说反了,10 是下界不是上界**,因为两个代理信号都在探针**下方**,
> 看过探针就离开的人不可见。因此正确的词是**「不确定」,不是「无意义」**:
> 如果真实曝光超过约 30,那 10% 的作答率**确实**被排除了;数据分不出是哪一种。

> ⚠️ **同时补一条调查漏掉的**:组件自己的头注释就指向了前一次实验,而且数据支持它——
> `recruit_banner_impression` **3,954** 次 / 点击 **1** / 关闭 4。
> 量是探针的 16 倍,方向和「曝光还不够」相反。但它**同样**是非视口计数,
> 而且 `COUNT(DISTINCT session_id) = 0`(session_id 全是 NULL),所以它也没有分母。

**做了什么**:保留 mount 事件(它是唯一的历史序列),**在旁边加一个真正的 `word_intent_seen`**
(`useImpression`,threshold 0.5 + 1s dwell,和站内其他曝光一致)。
`seen / mounted` 之后就是一个**直接测出来的可达率**,不用再推。

### 1. `src/lib/track.ts:37` —— **每一个数字都继承一个静默丢弃**

```js
if (navigator.sendBeacon) {
  navigator.sendBeacon(`${API_URL}/events`, new Blob([body], …));   // ← 返回值被丢掉
}
```

`sendBeacon` 在 UA 拒绝入队时**返回 false 而不抛异常**(每源 beacon 配额约 64KB、
unload 期间队列压力、部分加固/内嵌 webview 直接 stub 成 false)。
外面的 `try/catch` 只能接住 **throw**,接不住 **false**。
→ 事件没离开浏览器,应用什么也不知道,**没有任何计数器记录这次丢失**。

`else` 分支的 `fetch` 有 `.catch(() => {})`,同样吞掉;而且**有 sendBeacon 的浏览器永远走不到那个分支**。

**这条影响的不只是复制率 —— 是这个仓库里每一个事件计数,包括 §5 锚点和 AI kill-gate。**

### 2. `word_generated` 对四类真实用户根本不发 —— 而它是 **§5 锚点**

`word-color-generator-page.tsx:348` 的早返回在 `track(PAYWALL_EVENT.generated)`(:374)**之上**:

```js
if (!WORD_PAYWALL_ENABLED || proUser !== false || gated || isUnlocked()) return;
```

被静默排除的四类:
1. **Pro 订阅者**(`proUser === true`);
2. **会话还没解析出来的人**(`proUser === null` —— 打字快的人的前 ~200ms,
   以及任何 API 不可达的时刻,`pro-gate-policy.ts:97` 让 `sessionError` 产生 null);
3. **本次访问已经被墙的人** → 第 6、7、20 个词全部不可见,
   **每会话 `word_generated` 被硬顶在 5**;
4. **在这个浏览器里做过邮箱解锁的人**(读 localStorage)—— **永久,永远**。

`server/scripts/gate-report.cjs:214` 给这个指标打的标签是
**「§5 ANCHOR(utility ≥300/mo · shrink <150/mo 连续两个月)」—— 一条留存/砍掉的判据。**

> ⚠️ **这条直接波及 §1.5 那张「最远用到第几次」的表。** 「在上限 5 处堆积 23.8%」
> 至少**部分**是这个早返回造成的记录假象,不纯粹是用户行为。**§1.5 的结论要再查一次。**
