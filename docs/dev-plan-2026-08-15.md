## §1 分母已经存在 —— 要做的是**停止用错的那个**

第 1 稿说"第一方分析无法区分人和机器人"。**这句话只对 `pageviews` 成立。**

```sql
-- 没有访客标识,不可用作分母
CREATE TABLE pageviews (id, path, referrer, screen_width, created_at, channel, ...);

-- 有 session_id,而且事件是交互门控的 —— 这才是分母
CREATE TABLE events (id, event_name, props_json, user_id, session_id, path, ...);
```

**所以第 1 稿的 IP+UA 哈希、以及第 2 稿改用的 sessionStorage id,两个方案都在重造一个
已经存在的东西。** 都取消。

真正要做的三件事,都很轻:

1. **把所有报表的分母从 pageview 换成 `COUNT(DISTINCT events.session_id)`。**
   `server/` 里的周报、gate 报表、admin 面板都要改。
2. **确认 `server/bot-detect.js` 的过滤仍在工作**(07-26 部署,有 `[bot-filter]` 日志)。
   读一周日志,看丢弃率是否仍在合理区间。
3. **与 PostHog 的 session 数对表**(project 456902,**必须用 `query` schema**)。
   两边差异大就说明其中一套坏了,先修测量。

### 2.1-原文(第 4 稿,保留以便对照)

**每月约 650 次 Google 引荐落在 404 上**(`referrer` 是 `document.referrer`,是每次请求的真实来源,

|---|---|---|
| `/notes/nov-2027-color-in-ai-generated-design/` | Google | **592** |
| `/notes/sep-2027-color-in-email-design/` | Google | 42 |
| `/notes/oct-2027-color-grading-for-photographers/` | Google | 14 |

**我先前把成因写错了,已更正:** 不是 08-08 那次改动下线的。
`d0f6903`(**2026-03-31**)就引入了 `CUTOFF = "2026-12-31"`,当时就挡下了全部 53 篇 2027 文章。
08-08 把 CUTOFF 改成构建日期,新挡下的是**2026 年下半年**那批,是另一个集合。

**所以这三个 URL 只在三月上线了约 8–9 天,然后 404 至今四个半月 —— 却仍在每月吃到 648 次 Google 引荐。**
这让修复更值得做,不是更不值得。

**但不要直接"改日期重新发布"。** Codex 指出两个会造成实际损害的问题,均已核实:

1. **内容已过时。** 流量最大的那篇(592 次)把 **Midjourney v6 和 DALL·E 3 当作当前版本**;
   email 那篇写着"in 2027"。原样重新发布 = 在这个站被搜索最多的 URL 上发布错误内容。
2. **`date` 一个字段承担五种语义**:发布资格、页面显示日期、OG `publishedTime`、
   JSON-LD 的 `datePublished` **和** `dateModified`、sitemap 的 `lastModified`。
   把它改成三月,等于宣称一篇八月才审过的文章"最后修改于三月"。

**正确做法:**

1. **先逐篇事实核查**,改掉过时提法(Midjourney 版本、DALL·E 状态、"in 2027" 之类)。
2. **拆分字段**:引入 `status` / `publishedAt` / `updatedAt`(可选 `scheduledFor`),
   不要再让 `date` 一词多义。发布日期用真实的首次上线日,修改日期用今天。
3. **保留原 URL**。若要改掉 `sep/oct/nov-2027` 这种误导性 slug,
   **一对一 301 到对应文章是正确的**;只有多对一重定向到 `/notes/` 才是 soft 404。
4. **先去 GSC 核实**这三个 URL 的实际点击/曝光/收录状态,再决定投入多少。
   `referrer` 只能证明有 648 次带 Google 引荐的请求,不能证明当前排名。

**护栏不要查生产分析。** 我原本提的"构建时查近 90 天自然搜索流量,有流量就构建失败"是错的 ——
那会让构建依赖可变的线上数据和密钥。改为:**维护一份提交进仓库的"曾经发布过的 URL"清单**,
要求每个条目要么有活页面、要么有显式 redirect;流量与 GSC 另行监控。
