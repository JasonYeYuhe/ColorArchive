## §1 但是先停一下:这三万次是人吗?

**`pageviews` 表里没有任何访客标识** —— 无 IP 哈希、无 session id、无 UA:

```sql
CREATE TABLE pageviews (id, path, referrer, screen_width, created_at,
                        channel, utm_source, utm_medium, utm_campaign,
                        referrer_domain, landing_path);
```

所以第一方数据**在结构上无法区分**「三万人各看一页」和「一个爬虫看三万页」。
55% 的 direct 占比对一个 SEO 站来说偏高,这个数字本身就值得怀疑。

这个项目在 2026-07-26 吃过**一模一样**的亏:当时我把 1,025 次写入报成"真实用户
写入被丢弃",隔天审计推翻 —— 1,024 笔来自同一 IP 同一天,是洪水机器被正确限流。
教训写在案:**只看总数、不按 IP/按天分解,就会得出反过来的结论。**

PostHog 有 session 层数据(07-20 记录:`/word-to-color` 每周 276 sessions)。
按 276×4.3 ≈ 1,190 sessions/月,对上 6,351 PV/月是 5.3 PV/session —— 可能,
也可能两套系统在说不同的事。**没对齐之前,任何以"三万"为分母的转化率都是虚构的。**

> **§1 是本计划的前置条件。它没做完,后面每一阶段都不许开始。**

## §2 Phase 0 — 校准分母,顺手堵漏(第 1 周)

### 0.1 分母对齐(必须最先做)

1. 从 PostHog 拉近 30 天的 **unique visitors / sessions / pageviews**,按路由。
   凭证与项目号见 `reference_posthog_admin`(project 456902,**必须用 `query` schema,
   legacy `filters` 写入已禁用**)。
2. 与第一方 `pageviews` 逐路由对表,产出一张 `PV(第一方) / PV(PostHog) / sessions / uniques` 的对照。
3. 给 `pageviews` 加一列 **`visitor_hash`**(每日轮换盐 + IP + UA 的 HMAC,不存原始 IP)
   与 `is_probable_bot`,并复用 07-26 已有的爬虫过滤逻辑。**这是本阶段唯一允许的新建表结构改动。**
4. 输出一个数字:**近 30 天真实人类会话数**。后面所有分母都用它,不用 35,436。

**完成判据**:两套系统在 top-10 路由上的差异能被解释;`visitor_hash` 上线并回填至少 7 天。

### 0.2 已确认的漏(可直接修,证据在手)

- **652 次/月落在 404 上。** 08-08 给 newsletter 加了"不发布未来日期"的过滤(正确),
  但 53 篇 2027 年的文章此前已上线并被索引,现在 4 个路径合计 652 PV/月全部 404。
  实测:`/notes/nov-2027-color-in-ai-generated-design/` → **HTTP 404**,而它是全站
  **第 6 大** 访问页面(594 次)。
  **修法**:给这些 slug 加 301 到 `/notes/`(或最接近的同主题在售文章),并写一个
  测试:凡是被日期过滤挡下的 slug,必须在 `next.config.ts` 里有对应 redirect。
- **重跑一遍死链扫描。** 08-08 修过 137 个,但那次之后又改了 `/tools/*`、notes 过滤、
  guide 标题。用同一套脚本再扫一次,只报新增。

## §3 Phase 1 — 只测一个页面(第 2 周)

`/word-to-color/` 是全站 18% 的流量,是唯一有资格谈转化的页面。
其余 100 多个路由里,一周有 ≥2 会话的只有 9 个(07-20 实测)。

**不加功能,只装仪表。** 需要回答的是:那 6,351 次浏览的人**走去了哪里**。

必须打点(若已有则校验其正确性):
1. 落地 → 输入第一个词 的比例
2. 输入 → 复制任一色值 的比例
3. 触发付费墙(第 5 个词)的绝对次数
4. 付费墙 → 点击 `/pro/` 的比例
5. 付费墙 → 邮件解锁 的比例
6. 跳出:进来只看一页就走的比例

**完成判据**:能画出一张从 landing 到 `/pro/` 的漏斗,每一层有绝对数字,分母是 §2 校准过的人类会话。

### 为什么不同时测别的
07-20 已测:guides 有 274 会话/周但只有 1.15 事件/会话,工具点击率 7%。
再铺开测只会得到更多"低到无法优化"的数字。先把最大的那个搞清楚。

## §4 Phase 2 — 一次诚实的变现测试(第 3–5 周)

在 §3 漏斗最细的那一层做**一次**改动。**不是三次,是一次** —— 同时改多处
就没法归因,而这个站的流量还不足以跑并行实验。

候选(按 §3 的结果二选一,不要都做):

- **A. 如果漏斗断在"输入 → 复制"**:产品没被用起来,变现无从谈起。
  改动应在工具本身(§5 已知的 `/pick-for-me` 中文分词缺陷即属此类)。
- **B. 如果漏斗断在"付费墙 → /pro/"**:产品被用起来了但价格/时机/文案不对。
  改动应在付费墙那一屏。

**必须事先写死判据。** 参考 Design Notes 的做法:那次退役之所以干净,是因为
"292 次曝光 0 转化就退役"这条规则是**提前**写下的。

建议判据(在开工前由 owner 确认或修改):
> 改动上线后 14 个干净日,若 `/pro/` 点击的真实人类会话转化率 < 1.0%
> (rule of three:0/300 会话即可判定上限 <1%),则判定该漏斗层不是价格问题,
> 转入 §5。

## §5 决定,以及提前写好的规则

这一阶段的产出**不是功能,是一个决定**。三条路,现在就把判据写下来:

| 路 | 触发条件 | 含义 |
|---|---|---|
| **深耕** | §4 测试达标,或期间出现 ≥3 笔非试用付费 | 继续投入,进入下一轮功能开发 |
| **转公用事业** | §4 未达标,但 §2 校准后的人类流量 ≥ 15,000 会话/月 | 停止功能开发与变现改造;把成本压到最低,当作免费公共工具运行,保留 SEO 资产 |
| **收缩** | §4 未达标,且人类流量 < 5,000 会话/月 | 关停付费链路与后端 AI,静态化,只留域名与档案 |

**成本必须同时量化**:Vercel(峰值 $73.93/月,已修过 `ignoreCommand`)、
DigitalOcean droplet、域名、Resend、PostHog。若"转公用事业",目标是把月成本压到
一杯咖啡以内 —— 而这需要先知道现在到底是多少。

## §6 这份计划**不做**什么,以及为什么

- **不做新工具。** 已有 44 个,一周有 ≥2 会话的路由只有 9 个。第 45 个不会改变什么。
- **不做 Complete Archive 的推广。** 它历史成交 0 笔。今天刚修好它缺 70 个中性灰的
  缺陷(`0b89daf`),那是修正确性,不是投资。
- **不重启 Design Notes。** 0/292 已按预设规则判定,重启需要新证据而不是新文案。
- **不碰 Figma / VS Code 的商店文案。** 4 个用户;改动会触发商店重审(owner 红线),
  为 46 个颜色的措辞不值。
- **不做重构。** `scripts/generate-downloads.mjs` 里四个导出各自重建档案的坏味道已用
  断言覆盖(`assertBundleIntegrity`),重构的风险大于收益。

## §7 什么会证明这份计划是错的

写在前面,免得事后找补:

1. **§2 校准后发现三万次里绝大多数是机器人。** 那么"有流量没收入"这个前提消失,
   真正的问题变成"这个站几乎没有真实用户",§4 的变现测试没有意义,应直接进 §5。
2. **PostHog 与第一方数据无法对齐。** 那么两套都不可信,应先修测量再谈其他。
3. **iOS 数据门显示 App 有真实留存。** 那么重心应该在 iOS 而不是 Web,本计划需重写。
4. **owner 的目标不是收入。** 如果这个站的目的是作品集/公共资源,§4 和 §5 全部作废,
   只保留 §2 的堵漏和 §6 的克制。**这一条只有 owner 能回答,且应该先回答。**
